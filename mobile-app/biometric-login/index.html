    Dev notes

    Biometric login: scenarios & rules

    How it works

    Turning on biometrics stores a device-bound credential (refresh token or private key) in the iOS Keychain / Android Keystore, protected by Face ID or fingerprint. A successful scan unlocks it and the app gets a new session. No biometric data leaves the phone. The phone plus the biometric count as two factors, so biometric sign-in skips the password and the security code. Signing in with a password still needs the code (text or email, with native OTP AutoFill).

    Scenarios

    #ScenarioExpected behaviour

    iOS

    • LAContext with .deviceOwnerAuthenticationWithBiometrics (no device passcode fallback). localizedFallbackTitle = "Use password".
    • NSFaceIDUsageDescription: "Use Face ID to sign in to your Freedom account quickly and securely." iOS shows this permission alert once per install, the first time the app uses Face ID: when the customer taps Turn on Face ID on the offer or turns on Biometric login in Manage biometric login. OK continues to the scan; Don't Allow leads to scenario 3.
    • Keychain item with SecAccessControl .biometryCurrentSet, so adding a face or finger invalidates it.
    • Errors: authenticationFailed → retry alert · userFallback → password · userCancel → returning screen · biometryLockout → locked banner · biometryNotAvailable (access denied) / biometryNotEnrolled → password only.
    • Touch ID iPhones use the same flow with "Touch ID" copy.
    • Phone not set up / Face ID not allowed: tapping the OFF toggle in Manage biometric login opens a message with Go to Settings. iOS apps can only open their own page, Settings › Freedom (UIApplication.openSettingsURLString), which is right for "not allowed". There is no public link to Face ID & Passcode, so for "not set up" the copy gives the path and the button opens Settings. (Decision to confirm.)

    Android

    • BiometricPrompt with BIOMETRIC_STRONG and a CryptoObject from a Keystore key with setUserAuthenticationRequired(true) and setInvalidatedByBiometricEnrollment(true).
    • Negative button "Use password". Failed reads stay in the sheet ("Not recognized. Try again.").
    • Errors: ERROR_LOCKOUT (5 fails, 30 s) / ERROR_LOCKOUT_PERMANENT → locked banner · ERROR_NEGATIVE_BUTTON → password · ERROR_USER_CANCELED → returning screen · KeyPermanentlyInvalidatedException → biometrics changed · BIOMETRIC_ERROR_NONE_ENROLLED → password only.
    • No fingerprint enrolled: the Go to Settings button opens enrollment with Settings.ACTION_BIOMETRIC_ENROLL (Android 11+, extra BIOMETRIC_AUTHENTICATORS_ALLOWED = BIOMETRIC_STRONG). Fall back to ACTION_FINGERPRINT_ENROLL (Android 9–10) or ACTION_SECURITY_SETTINGS.

    Rules

    • One account per phone can use biometrics. Switching accounts turns it off and deletes the key on the phone and the server.
    • The offer to turn it on shows once, after the first sign-in with password + code. After "Not now", it's only in Manage biometric login. It shows again after biometrics change on the phone.
    • Turning it on and off needs a scan to confirm turning it on, and a confirmation to turn it off.
    • Sign out keeps biometrics on; the next sign-in can use it. (Assumption to confirm.)
    • The server revokes the biometric credential when the password is changed or reset, the account is locked, or after inactivity (e.g. 90 days). The app then asks for the password.
    • The OS limits the number of tries (iOS 2 per prompt, 5 total; Android 5). The app doesn't count tries itself.
    • Biometric sign-in failures never lock the Freedom account; only password failures do.
